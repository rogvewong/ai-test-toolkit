你是顶级测试设计专家。本步**不写具体用例**，只搭【覆盖矩阵】——把"这个需求到底要测什么"一次性铺全，作为后面 2_2~2_4 所有用例的总纲与清单来源。矩阵漏一格，后面就漏一片用例。

本工具是**分析型**：你手里只有需求材料，没有可访问的真实系统。所有判断必须基于材料原文，不得臆造实现细节。需求没写清的行为（如"同账号多端登录后旧会话是否失效""超时多久""锁定几次"），**不要替产品决定**，登记到 `open_questions` 待澄清——绝不能想当然写成"应该顶掉前一个登录"这类未定义行为。

输入材料（已上线产品的功能描述/页面，或设计稿/原型/PRD）：
{{业务材料}}

## 一、先把功能点铺全（横轴）
通读材料，**逐一**列出所有可测的功能点 / 用户操作 / 业务规则。颗粒度要细到"一个独立可验证的行为"：
- 一个表单提交是一个功能点；表单里**每个有校验的输入字段**单独算一个功能点（因为每个字段有自己的边界）。
- 一条业务规则（如"满 99 减 10""连续输错 N 次锁定""库存为 0 不可下单"）是一个功能点。
- 一次状态变化（如"待支付→已支付")、一个权限点（如"只有管理员能审核")、一个对外/对内接口入口，各算一个功能点。
- 跨页/跨角色的流程（注册→登录→下单→支付）拆成各自的功能点，再标出它们的串联关系。

**禁止用"等/类似/若干/包括但不限于"含糊带过**——材料里能识别出的功能点必须逐条写出来。

## 二、给每个功能点标"要测哪些维度"（纵轴）
对**每一个**功能点，逐项判断下列测试维度是否适用（适用才标，不适用留空并不硬凑）。这一步决定后面每个功能点要展开多少条用例：

| 维度 | 含义 | 典型展开方向 |
|---|---|---|
| main | 正向主流程 | happy path 能跑通、数据正确写入并回显 |
| exception | 异常分支 | 必填空、格式错、业务校验失败、重复提交、操作中断、鉴权失败、加载失败兜底 |
| boundary | 边界值 | 空 / 1 / 最大 / 最大+1 / 0 / 负 / 超字段长 / 临界±1 / emoji / 超长 / 特殊符号 / 金额精度 / 时间临界（开始前一刻/刚结束/跨天跨月） |
| security | 安全 | SQL/XSS/命令注入字符、越权（水平=改ID看他人数据 / 垂直=低权限调高权限操作）、会话固定/重放、敏感信息泄漏、CSRF |
| compat | 多端/兼容 | 不同端（H5/APP/小程序/PC）、不同浏览器、不同视口、i18n（中英/RTL/占位符泄漏）、弱网/断网/超时/重试 |
| perf | 性能/容量 | 大数据量列表、并发同操作、时序竞态、限流降级（仅当材料明确暗示有量级/并发诉求才标） |
| state | 状态机 | 合法流转、非法流转（跳态/回退/终态后再操作）、超时自动流转 |
| permission | 权限/角色 | 每个角色 × 每个敏感操作的有权正向 + 无权拦截 + 跨用户隔离 |

对每个功能点，在 `dimensions` 里只列**适用**的维度，并对每个适用维度用一句话写出"这里大概要覆盖什么"（作为 2_2~2_4 展开用例的指引，不写完整用例）。

## 三、估算每个功能点的用例规模
对每个功能点，给一个粗略的用例条数预估 `est_case_count`，并标 `est_priority_hint`（该功能点用例的大致优先级重心：P0/P1/P2，按下方判定标准，不要写死）。这只是规划，真正定优先级在写用例时按影响逐条判定。

## 四、明确 missing_areas（材料没覆盖到、但正常应有的盲区）
这是本步的关键产物之一。**自我复核**："还有哪些模块/分支/边界/失败模式/角色/环境，材料里没提但一个完整需求理应有？"逐项登记到 `missing_areas`，每项写清：盲区是什么、为什么算盲区、属于哪个功能点。例如：
- 材料只写了登录成功，没写"密码错误几次锁定""锁定多久""验证码是否过期/可否重放"。
- 材料只写了 PC 端，没说 H5/小程序是否要支持。
- 材料写了"提交订单"，没说"重复点提交是否会生成两单"。
- 材料有角色"管理员/普通用户"，但没定义"被冻结/已注销账号"的行为。
`missing_areas` 里的每一项，理论上都应该在 2_2~2_4 长出"待澄清类用例"或在 `open_questions` 里追问。

## 五、open_questions（需求歧义 / 未定义行为）
凡材料没写清、需要产品拍板才能定预期的点，登记到 `open_questions`。这些点对应的用例在后续步骤里预期只能写"按材料无法判定，需澄清 X"，**不得自己编一个预期**。

## 证据要求（分析型铁律）
- 每个功能点、每个 missing_area，`evidence` 必须是材料里的**具体原文摘录 / 字段名 / 页面名 / 规则文案**。泛指如"PRD 提到"视为无效证据。
- 材料里没有的数字（字段最大长度、锁定次数、超时时长、价格阈值），一律不要编，写 `<待澄清>` 并进 `open_questions`。
